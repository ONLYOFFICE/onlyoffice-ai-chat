# Icons and theme tokens

This skill covers two of the repo's three code generators — icons and
theme tokens (the third, i18n, has the `add-translation-key` skill). Both
work the same way: put the file in place, then regenerate the type. Both
generated files carry an `AUTO-GENERATED` header — never hand-edit them,
and `prebuild` regenerates them anyway.

## Icons

There are **two separate image namespaces**, and conflating them is the
easy mistake.

### 1. The general icon set — feeds `IconName`

`IconName` in `src/ui/providers/ImagesProvider/generated-types.ts` (62
entries today) is generated by merging the names found in four
directories:

| Directory | Contents |
| --- | --- |
| `src/assets/` (root) | `*.svg` |
| `src/assets/light/` | `*.png`, 245 files |
| `src/assets/dark/` | `*.png`, 245 files |
| `src/assets/formats/` | file-format icons |

Two things about the naming:

- **Light/dark is decided by the directory, not by the filename.** Both
  folders hold the *same* base names (`arrow.bottom.png` in each) — there
  is no `_light`/`_dark` suffix here. Add your PNG to both folders under
  the same name, or the icon breaks in one theme.
- **Density variants collapse.** The generator strips an `@<n>x` suffix,
  so `arrow.bottom.png`, `arrow.bottom@1.25x.png` and
  `arrow.bottom@1.5x.png` all contribute the single name `arrow.bottom`.
  Names may contain dots.

Then regenerate:

```
npm run generate:icons
```

### 2. Provider logos — a separate namespace, no codegen

`src/assets/providers/light/` and `dark/` use a **different** convention:
`<key>_light.png` / `<key>_dark.png`. These are **not** in `IconName` and
never will be — the generator's `providers` bucket reads
`src/assets/providers/`, which holds only the two subdirectories, so it
contributes nothing. That is intentional, not a bug to fix:
`shared/images.ts` glob-imports these folders eagerly and resolves them
through the `PROVIDER_ICON_NAMES` map via
`getProviderImageSrc(providerType, theme)`, explicitly kept out of the
general collections. Adding a logo means the two PNGs plus a map entry —
no `generate:icons` run. Unmapped providers fall back to
`custom_provider_<theme>.png`. See the `add-ai-provider` skill.

### Drawing a new SVG

The `Icon` component (`ui/components/icon/`) loads the asset by URL
through `react-svg` and then **recolors the live SVG DOM at runtime**:
each shape is recolored by the paint it already declares — an element
with an explicit `stroke` gets its stroke recolored, one with `fill` gets
its fill, one with both gets both, and one with neither falls back to the
caller's `isStroke` hint. So a new SVG must declare `fill` or `stroke`
explicitly on its shapes; an icon relying on inherited or default paint
will not recolor. (`vite-plugin-svgr` is configured in `vite.config.ts`
for `*.svg?react` imports, but no library code uses that path — don't
introduce it for icons.)

Hosts can override any icon at runtime via `ImagesProvider` — see
`docs/ui/providers/images.md`.

## Theme tokens

`ThemeTokens` is generated from the custom properties declared in
**`src/ui/styles/theme-light.css`** — that file alone defines the token
*set*. Each theme file is one class selector (`.theme-light`,
`.theme-dark`, …) over the seven files:
`theme-light`, `theme-dark`, `theme-classic-light`, `theme-contrast-dark`,
`theme-gray`, `theme-night`, `theme-white`.

The token set is **not uniform across themes**, and that is deliberate:

- **Colour tokens** (~200 of them) are defined in all seven files, each
  with a theme-appropriate value. A colour token missing from a theme
  renders unset there.
- **Sizing and typography tokens** (`--aui-font-base`, `--aui-font-scale`,
  `--combo-box-height`, the `*-font-size` / `*-font-weight` family) are
  theme-independent. They live once in `theme-light.css`, with defaults
  also declared in `src/ui/styles/index.css`. Don't copy these into the
  other six files.

Adding a token:

1. Declare it in `theme-light.css`.
2. If it is a **colour**, add a value to the other six theme files. If it
   is sizing or typography, leave them alone and check whether it also
   belongs in `index.css` as a documented knob.
3. Regenerate:
   ```
   npm run generate:theme
   ```
4. Use it as `bg-[var(--your-token)]` — never a Tailwind palette
   utility or a raw hex (see the `code-style` skill).

Nothing checks that the theme files agree. For a colour token, grep it
across `src/ui/styles/theme-*.css` and confirm seven hits before
committing.

## The CSS scoping rule

Everything the build emits under Tailwind's `@layer base` is rewritten by
`scripts/scope-preflight.mjs` to sit under `:where(.aui-root)`, so the
widget never restyles the host page. Don't add selectors that assume they
own `html` or `body` — and don't "fix" a specificity problem by escaping
that scope.
